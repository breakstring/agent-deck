# Agent Deck 旋钮与控制台灯光配置设计

状态：已确认，待实施
日期：2026-07-10
范围：硬件无关的旋钮能力、旋钮动作、控制台灯光、虚拟面板反馈和跨平台系统控制；第一验证设备为 MiraBox N4 Pro。

## 背景

Agent Deck 已完成上方 LCD 按键的用户配置，并在 N4 Pro 的 logical panel 上实现品牌待机、Quota
和 Usage 内容。下方 4 个旋钮及灯圈目前尚未进入用户配置，也没有形成可适配其他硬件型号的能力模型。

本设计解决以下问题：

- N4 Pro 的 4 个完整旋钮不应变成未来硬件的固定模板。
- 用户可以把任意旋钮放在任意位置，允许多个旋钮绑定同一动作，也允许不设定。
- 旋转、按下和 LED 必须是三种独立能力；LED 不应被伪装成每个旋钮都可独立控制。
- touch bar 不增加常驻文字状态带，但旋钮操作仍需有足够清楚的即时反馈。
- macOS 与未来 Windows 的音量、麦克风、显示器亮度控制必须按实际可用能力降级。

## 产品目标

1. 用硬件 capability 而不是 N4 Pro 固定布局描述旋钮、按下、灯光和亮度能力。
2. 用户可以独立设置每个旋钮的旋转与按下动作；相同动作可重复绑定。
3. 灯光配置作为设备级 surface 设置，不嵌在某个旋钮的动作设置里。
4. N4 Pro 的预览、配置草稿和真实硬件下发保持分离：编辑只更新 GUI 预览，保存并应用后才写设备。
5. 第一阶段只提供低风险、本机、可验证的系统控制，不把 Agent 反馈、审批或文本输入塞进旋钮。

## 非目标

本阶段不做：

- Agent 反馈、选项选择、审批确认或其他 Agent 响应动作。
- Agent 概览、Agent 详情滚动、子 Agent 浏览或 Agent 选择器。
- 旋钮长按、双击、触摸感应等 SDK 未验证输入。
- 任意 shell、文本注入、任意 App 启动或媒体播放控制。
- 为每个未来硬件型号给出完整默认布局。
- N4 Pro 按键屏、secondary screen、touch bar 分别设置亮度。
- 基于 quota、daemon 健康或 Agent 状态的用户可编程灯光规则。

## 术语

### 旋钮控制单元

一个物理旋钮位置，例如 N4 Pro 的 `knob_1`。它的能力由三个彼此独立的通道组成：

```text
rotate: 左右旋转输入
press:  按下输入
light:  与该位置关联的灯光输出；可能不存在，也可能无法单独寻址
```

`rotate` 和 `press` 只决定该位置能接收哪些用户动作；`light` 不属于动作 binding。

### 灯光区域

设备实际可被 SDK 设置的 LED / 背光输出单位。它不必与旋钮一一对应。灯光区域的寻址粒度为：

```text
none        没有可控灯光
global      整台设备只有一个统一灯光输出
group       一组物理灯共用同一种设置
per_control 每个旋钮或控制单元可独立设置
```

配置 UI 必须按灯光区域显示，不能根据设备外观猜测其是否可独立寻址。

### 系统显示器亮度目标

用于“调节系统显示器亮度”的全局目标，不属于任意一个旋钮 binding。它是本机扫描到的、被当前
平台后端明确判定为可读写亮度的显示器。

## 硬件能力模型

设备 profile 应由以下能力分别描述：

```text
rotary_controls[]
  id
  supports_rotate
  supports_press

light_zones[]
  id
  addressability
  associated_control_ids
  supports_color
  supports_brightness
  supports_breathe

display_brightness
  supports_set
  scope: device_global | per_surface
```

没有某项能力时，配置页不显示相应字段；不能用 disabled 但可见的控制制造“这个设备好像支持”的错觉。

### N4 Pro 当前 profile

| 能力 | 当前结论 | 产品处理 |
| --- | --- | --- |
| 旋转 | 4 个旋钮均支持左右旋转 | 显示 4 个独立旋钮配置入口 |
| 按下 | 4 个旋钮均支持按下 | 每个入口显示独立按下动作 |
| 控制台亮度 | SDK 提供 `set_brightness(percent)` | 作为“调节控制台屏幕亮度”独立动作；按设备整体处理 |
| 控制台子 surface 亮度 | 未发现按键/touch bar 分开亮度 API | 不提供分开设置 |
| RGB LED | SDK 声明 4 个 LED，但高层调用统一按数量设置颜色 | 作为单个 `rotary_ring_group` 灯光区域，不显示 4 个独立颜色 |

上游 Python SDK 的 `init()` 会先将设备亮度写成 `100`。因此实施“调节控制台屏幕亮度”后，daemon
必须持久保存用户当前值，并在每次设备 `init()` 完成后重新写回。N4 Pro 当前的 LED 控制需要在实施前
做一次显式真机 smoke：确认颜色、亮度和安全刷新频率；在通过前不能声称呼吸效果已在真机可用。

## 配置模型与 GUI

### 旋钮入口

配置页沿用设备预览作为空间入口，而不是建立“旋钮 1 到旋钮 4”的独立表格。用户点击 N4 Pro 预览中的
一个旋钮后，检查器显示该位置实际拥有的输入能力。

```text
旋钮 3
  左右旋转：动作选择
  按下：动作选择
```

配置中的“旋钮 3”只表示物理位置，不预设其产品角色。所有旋钮可以：

- 绑定不同动作。
- 绑定相同动作。
- 只配置旋转或只配置按下。
- 保持暂不设定。

### 灯光入口

灯光是独立的“控制台灯光”区域，不出现在单旋钮检查器内。

N4 Pro 初始显示：

```text
控制台灯光
  N4 Pro 旋钮灯圈组
    关闭
    基础色
    效果：静态
    柔和呼吸：仅在 profile 经真机 smoke 验证后显示
```

如果未来 profile 报告 `per_control` 灯光区域，UI 才显示“旋钮 1 灯圈”“旋钮 2 灯圈”等独立项。若只有
global 或 group 能力，预览和真机都必须整组同步变化。

### 草稿预览与应用

旋钮、灯光或系统目标的任何编辑都先进入 draft：

```text
编辑配置
  -> GUI 的硬件预览立即变化
  -> 页面标记为“配置有改动”
  -> 真机保持上一次已应用配置

保存并应用
  -> 原子保存配置
  -> 重新计算所有 surface、旋钮和灯光输出
  -> 在同一硬件会话内下发可组合的 N4 Pro 更新
```

例如用户为 N4 Pro 灯圈组选择青色时，预览内 4 个旋钮灯圈应立即统一显示该颜色；真实灯圈只在保存并应用后更新。
若 profile 已通过真机 smoke 验证呼吸效果，预览才额外呈现该效果。预览不得把当前 N4 Pro 显示成 4 个可独立设置不同颜色的灯圈。

## 第一阶段动作

### 旋转动作

| 动作 | 行为 | 参数 |
| --- | --- | --- |
| `unassigned` | 不做任何事 | 无 |
| `cycle_virtual_panel` | 左右循环可手动浏览的 logical panel | 无 |
| `cycle_panel_content` | 左右循环当前 panel 的内容维度 | 无 |
| `adjust_output_volume` | 调节系统默认输出设备音量 | 每格固定 2% |
| `adjust_input_volume` | 调节系统默认输入设备音量 | 每格固定 2% |
| `adjust_system_display_brightness` | 调节已选定的系统显示器亮度 | 每格固定 2% |
| `adjust_deck_display_brightness` | 调节控制台整体显示亮度 | 每格固定 2% |

第一阶段不显示步长配置。多个旋钮绑定同一连续动作时，使用相同的 `2%` 固定步长。

### 按下动作

| 动作 | 行为 |
| --- | --- |
| `unassigned` | 不做任何事 |
| `toggle_output_mute` | 读取系统实际状态后切换系统默认输出设备静音 |
| `toggle_input_mute` | 读取系统实际状态后切换系统默认输入设备静音 |

不提供“设为静音”或“取消静音”这类单向动作。切换语义更适合单个物理按下，也能避免用户为同一目标配置
互相依赖的两个旋钮。

## Virtual Panel 与反馈

### 手动轮换的面板

可手动轮换的固定顺序为：

```text
Brand -> Quota -> Usage -> Brand
```

Brand 是正常的归位和待机面板，必须进入轮换。Agent 概览、Agent 详情、反馈、审批、错误和连接异常不进入
这个普通轮换：它们会在后续以上下文进入或打断覆盖的方式另行设计。

面板内内容为：

```text
Brand: 无
Quota: 5h <-> Week
Usage: Day <-> Week <-> Month <-> All
```

当 `cycle_panel_content` 作用于 Brand 时，安静 no-op；它绝不能隐式切换到另一个 virtual panel。

### 不做常驻状态带

touch bar 不保留任何长期占用空间的旋钮文字说明。反馈按动作类别区分：

| 用户操作 | 视觉反馈 |
| --- | --- |
| 切换 virtual panel | 面板内容直接切换，无额外 HUD |
| 切换 panel 内容 | 图表或 quota 内容直接更新，无额外 HUD |
| 调节音量或亮度 | 中央短暂大号图形 HUD，展示图标和百分比 |
| 切换静音 | 短暂红色静音 HUD |
| 无能力、失败或不可用 | 短暂错误反馈后恢复原 panel |
| Brand 上切换内容 | 安静 no-op |

连续数值 HUD 每次旋转都会更新数值并重置隐藏计时；停止约 1.5 秒后恢复原 panel。HUD 仅在操作时出现，
不能演变成固定的状态条。

## 灯光行为

### N4 Pro 当前阶段

N4 Pro 当前只有一个可配置的旋钮灯圈组。它的常态只表达用户选择的视觉氛围：

```text
关闭
基础色 + 静态
基础色 + 柔和呼吸（仅在真机 smoke 验证后启用）
```

成功旋转或按下可以让灯圈组按基础色短暂提亮；操作失败可短暂红闪后恢复基础状态。由于灯光不能按旋钮独立
寻址，N4 Pro 第一阶段不把持续音量等级、输出静音或麦克风静音投影到灯圈：统一长期变红会掩盖用户选定的
氛围颜色，且无法说明是哪一个旋钮或哪一路音频发生了变化。

### 未来独立灯圈设备

当 profile 提供 `per_control` 灯光区域时，才允许将各旋钮基础色与其控制语义结合：

- 连续值可以在基础色可见亮度范围内映射数值。
- 输出或麦克风静音可以稳定显示红色。
- 非零连续值必须保留最低可见亮度，不能把低数值误显示为熄灭。

这仍然不是用户可编程规则系统；仅是 Agent Deck 为明确、已验证动作提供的受限状态表达。

## 跨平台系统控制

### 音频

输出和输入控制都针对操作系统当前默认音频设备。执行器必须先读取真实系统状态；尤其静音切换不能依赖
Agent Deck 的过期缓存。读取或写入失败时，不应报告成功，并以短暂错误反馈结束。

### 系统显示器亮度

系统显示器亮度目标通过一个独立的 capability scan 解析：

```text
无可控目标
  不显示“调节系统显示器亮度”动作。

唯一可控目标
  自动选中。

多个可控目标
  用户在全局设置中选择一台；初始建议为系统主显示器。
```

目标不能跟随鼠标位置。这样可避免用户移动鼠标后，下一次旋转突然操作到另一块屏幕，也能避免把不支持亮度
控制的外接屏误当成可用目标。

macOS 的内建屏与部分外接屏可能支持亮度调节，但不能假定所有外接屏都有可供第三方稳定控制的能力。Windows
可以通过 WMI 控制部分内建屏，并通过 DDC/CI 控制声明 brightness capability 的外接屏；DDC/CI 的真实可用性
仍必须按具体设备探测和验证。因此两个平台都以 capability scan 的实际结果为准，而不按操作系统名称承诺。

## 安全、错误与缓存边界

- 所有硬件输入仍先归一为 `InteractionIntent`，再由动作执行层访问系统音频、显示器或 SDK。
- 连续输入需要节流/合并，避免每个物理编码器抖动都触发一次昂贵的系统或 HID 写入。
- 音频、系统显示器亮度和控制台亮度分别缓存最后确认值；短 TTL 或动作执行后主动刷新，不能长期相信本地写入结果。
- 冷启动时读取 quota、Usage、音频和亮度可用状态；硬件下发优先使用已确认的缓存，后台再刷新。
- 设备初始化、系统目标消失、SDK 写入失败或权限不足时，配置草稿不丢失，真机保留上一次成功状态，并在 GUI 中给出明确失败诊断。
- Agent 反馈、审批、文本输入和任意 shell 始终不进入本阶段旋钮动作列表。

## 实施分期

### 阶段 1：能力与配置数据

1. 将旋钮能力从 `count + has_press` 拆成按控制单元描述。
2. 增加灯光区域和寻址粒度，修正 N4 Pro 为单一 `rotary_ring_group`。
3. 增加旋转、按下、灯光、系统显示器目标的持久化草稿配置模型。
4. 增加 capability-based 配置过滤和配置迁移默认值。

### 阶段 2：GUI 预览与应用

1. 在设备预览内支持选择可用旋钮并打开检查器。
2. 实现独立控制台灯光区，预览立即更新但不写硬件。
3. 将“保存并应用”扩展为一次性下发 key、panel、旋钮和灯光状态。
4. 为 N4 Pro 预览严格反映 LED group 限制。

### 阶段 3：动作执行与反馈

1. 接入系统输出/输入音量、静音、控制台亮度与可控系统显示器亮度执行器。
2. 实现 Brand / Quota / Usage 轮换、内容轮换和 no-op 边界。
3. 实现短暂中央 HUD、错误反馈、旋钮输入节流与缓存刷新。
4. 在 N4 Pro 真机验证控制台亮度和灯圈组颜色/亮度的真实行为。

## 验收标准

1. 同一配置模型可表示零个、一个或多个旋钮，以及旋转/按下能力不对称的设备。
2. N4 Pro 4 个旋钮可分别绑定旋转与按下动作，重复绑定和暂不设定均有效。
3. N4 Pro 的灯光 GUI 只显示一个旋钮灯圈组，编辑会立即更新预览，未应用前不改变真机。
4. Brand、Quota、Usage 的轮换与内容切换满足既定顺序，Brand 内容切换安静 no-op。
5. 连续动作固定每格 2%，连续 HUD 无常驻状态带且能在停止后恢复原面板。
6. 系统显示器亮度只对 capability scan 确认的目标开放；多显示器时不会跟随鼠标。
7. 音频/亮度/SDK 操作失败不会伪报成功，也不会损坏已应用的硬件配置。
8. 自动化测试继续保留 fake hardware；N4 Pro 的亮度和 LED 另有显式真机 smoke 记录。

## 实施前真机验证项

- N4 Pro 的 `set_brightness(percent)` 是否同时影响主按键、secondary screen 和 logical panel，以及最小/最大可见范围。
- N4 Pro 的 RGB LED 高层调用在当前 macOS SDK 下是否可实际设置颜色和亮度，安全刷新频率是多少。
- 灯圈组是否支持足够平滑的呼吸效果；若不支持，应在 GUI 中隐藏“柔和呼吸”。
- macOS 当前设备上的可控系统显示器枚举结果，以及外接显示器的读写和恢复行为。
- Windows 后端实现时，分别验证 WMI 内建屏路径与 DDC/CI 外接屏路径，不把任一接口的存在视为通用保证。
