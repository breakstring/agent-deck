# Agent Deck 显示外观与基础背景色设计

状态：已实施，待 N4 Pro 真机视觉验收

日期：2026-07-23

范围：Agent Deck 生成并下发到硬件显示表面的基础背景色；第一验证设备为妙联宝 N4 Pro。

实现说明（2026-07-23）：

- 已增加独立 `DeckAppearanceSettings`、版本化持久化和
  `GET/PUT /ui/display-appearance`。
- 已接入 App、URL、自动/自定义快捷键、状态 Key、Agent 动画、宠物 Key、宠物群体、
  Brand、Quota、Usage、Message 与 N4 Pro 全背景合成路径。
- 已为 App/URL/快捷键/状态/面板/宠物缓存加入外观身份；Agent RGBA 动画帧在 daemon
  生命周期缓存中按背景色派生，不覆盖仓库源帧。
- Web 已提供与 Touch bar 设置平级的“显示外观”入口、Key + Touch bar 双预览和
  `None` 恢复默认语义；草稿只在浏览器预览，保存后才应用。
- Touch bar 内容直接绘制在基础画布上，不再额外绘制 Brand、Quota、Usage 等面板的
  外层圆角底板或 PETS 地平线；宠物群体中的远程宠物光圈收窄为 `96 × 16` 像素。
- 快捷键自动图标的标签直接绘制在 Key 基础背景上，不再叠加内层圆角底板和描边。
- 自动化验收覆盖默认像素兼容、深浅色对比度、跨表面背景、Agent 透明帧派生、
  持久化/API/revision 与入口归属；真实 N4 Pro 仍需按 15.3 节人工检查。

## 1. 背景

当前不同内容渲染器各自使用固定的深色背景：

- App、URL 和自动快捷键 Key 使用近似 `#0B0E12` 的底色。
- 状态 Key 使用近似 `#0A0E16` 的底色，并在其上绘制卡片和语义色。
- 宠物 Key、App Key 宠物覆盖层和 PETS 面板使用近似 `#0B0F16` 的底色。
- N4 Pro Touch bar 面板使用近似 `#0E121C` 的底色。
- 自定义快捷键图标在上传归一化时已经合成为 RGB 图片，其透明区域也被烘焙为固定深色。

这些颜色都属于 Agent Deck 的渲染实现，而不是硬件提供的透明背景。N4 Pro 最终接收的是已经合成完成的 RGB/JPEG 或 RGB/PNG 图像，因此如果需要改变背景色，必须在 Agent Deck 生成画布和派生图像时完成。

问题最初由部分宠物在当前深色背景下观感不佳引出，但需求并不属于“宠物设置”。同一背景也会影响普通 App 图标、URL 图标、自定义快捷键、状态图、Agent 动画以及 Touch bar 虚拟面板。若只在 PETS 面板中增加设置，会形成错误的产品归属和不一致的渲染行为。

## 2. 已确认的产品结论

基础背景色是一个独立的“显示外观”设置，具有以下边界：

1. 它与宠物无关。宠物只是使用该外观设置的内容类型之一。
2. 它与 Touch bar 设置无关。Touch bar 设置只管理 Touch bar 特有的内容和交互，例如当前 PETS 面板的远程来源和巡游速度。
3. 它同时影响 Key 和 Touch bar 上由 Agent Deck 负责生成的基础画布。
4. 它不属于 Web 控制台主题，也不控制实体按键灯、背光或设备亮度。
5. 用户可以选择“不设置”或指定一个不透明颜色。

因此，设置层级建议为：

```text
设备配置
├── 按键设置
├── Touch bar 设置
├── 显示外观
└── 灯光与亮度（未来或已有设备能力）
```

## 3. 目标

- 提供一个跨内容、跨显示表面的可选基础背景色。
- 未设置时保持现有渲染结果和各渲染器当前默认值，不造成视觉迁移。
- 设置后让所有适用的 Key 和 Touch bar 内容使用同一个用户背景色。
- 在浅色和深色背景上都保持文字、分隔线和辅助图形可读。
- 让设置与硬件型号解耦，由渲染层解释，硬件适配器只负责下发最终图像。
- 明确透明素材、非透明素材、语义色和缓存的处理规则，避免出现“有的页面变了、有的页面没变”的隐式行为。

## 4. 非目标

第一版不包含：

- 修改 App、favicon、宠物、Agent 或用户上传图片本身的非透明像素。
- 用用户背景色替换警告、成功、错误、额度等业务语义色。
- 为每一个 Key、每一种面板或每一种内容分别设置背景色。
- 支持带透明度的颜色；第一版仅接受不透明 `#RRGGBB`。
- 根据图片内容自动取色、生成渐变或动态主题。
- 改变 Web 控制台自身的明暗主题。
- 改变 LED、按键背光、Touch bar 亮度或设备休眠策略。

## 5. 术语

### 5.1 基础画布背景

渲染器在绘制图标、文字、卡片或动画前创建的最底层像素。用户设置只直接替换这一层。

### 5.2 内容像素

App 图标、favicon、宠物精灵、Agent 动画帧和用户上传图片中的非透明像素。第一版保持原样。

### 5.3 语义图层

用于表达状态或层级的卡片、警告色、成功色、额度进度、选择框、遮罩和交互反馈。它们不被直接替换为背景色，但其中的中性色应根据背景推导，以维持对比度。

### 5.4 外观覆盖值

用户显式指定的基础背景色。未指定时为 `None`，由每个渲染器继续使用自己的既有默认值。

## 6. 配置语义

建议增加独立、不可变的外观配置模型：

```python
class DeckAppearanceSettings(BaseModel):
    """定义 Agent Deck 生成硬件画面时使用的全局显示外观。"""

    model_config = ConfigDict(frozen=True, extra="forbid")

    background_color: str | None = None
```

`background_color` 的语义如下：

| 值 | 行为 |
| --- | --- |
| `None` | 不覆盖背景色；每个渲染器继续使用当前默认值，确保升级前后像素级兼容。 |
| `#RRGGBB` | 覆盖所有适用渲染器的基础画布背景。保存时规范化为大写十六进制。 |

需要严格拒绝简写色值、透明色、命名颜色和非法字符，避免不同渲染路径产生不同解释。

渲染时不应只传递一个裸字符串，而应由统一解析器生成不可变的调色板，例如：

```python
class RenderPalette(BaseModel):
    """提供一次渲染所需的背景色及其对比色。"""

    model_config = ConfigDict(frozen=True)

    background: tuple[int, int, int]
    foreground: tuple[int, int, int]
    muted_foreground: tuple[int, int, int]
    surface: tuple[int, int, int]
    divider: tuple[int, int, int]
```

当 `background_color is None` 时，解析器需要保留各渲染器既有的背景和配套颜色，而不是强行把所有默认值统一为一个颜色。这样可以保证“不设置”的含义是真正维持当前行为。

## 7. 设置入口与交互

Web 控制台增加独立的“显示外观”设置区，不放入 PETS 或 Touch bar 设置。

第一版交互建议：

- “使用默认背景”与“自定义背景”两种状态。
- 自定义状态提供颜色选择器和 `#RRGGBB` 文本输入。
- 同时展示一个 Key 预览和一个 Touch bar 预览，至少包含透明图标、文字和语义卡片。
- 修改草稿时只刷新 Web 预览。
- 用户点击“保存并应用”后，才持久化配置并刷新真实硬件。
- “恢复默认”将值保存为 `None`，不是保存某个当前默认色的副本。

Touch bar 设置区继续承载 PETS 远程来源、巡游速度等面板特有设置。未来出现非 PETS 的 Touch bar 内容后，也仍按“表面特有行为”归入 Touch bar 设置，而不是按当前内容名称建立顶层分类。

## 8. 覆盖范围

| 内容 | 基础背景是否受影响 | 保持不变的部分 | 备注 |
| --- | --- | --- | --- |
| 普通 App Key | 是 | App 图标非透明像素 | 透明区域和 contain 留白显示用户背景。 |
| URL / favicon Key | 是 | favicon 非透明像素 | 规则与 App Key 相同。 |
| 自动快捷键图标 | 是 | 图标主体和业务语义色 | 中性按钮面、文字和描边由调色板推导。 |
| 自定义快捷键图标 | 是 | 用户图片非透明像素 | 必须从保留的 RGBA 源图重新合成，不能继续复用已烘焙背景的 RGB 成品。 |
| Agent 状态 Key | 是 | 状态动画或静态图的非透明像素 | 对已有不透明预渲染帧，需要重新生成或改为可合成源素材。 |
| 额度、用量等状态 Key | 是 | 额度色、警告色、进度语义色 | 外层背景改变；卡片、文字和分隔线按对比度推导。 |
| 独立宠物 Key | 是 | 宠物精灵非透明像素 | 宠物周围的透明区域使用用户背景。 |
| App Key 宠物覆盖层 | 是 | App 图标与宠物非透明像素 | 两个内容层共同合成到同一基础背景。 |
| Touch bar Brand 面板 | 是 | Logo 和品牌语义元素 | 空白区域及中性装饰适配背景。 |
| Touch bar Quota / Usage 面板 | 是 | 业务语义色 | 卡片层次和文字按调色板推导。 |
| Touch bar PETS 面板 | 是 | 宠物精灵和前景装饰 | 背景归显示外观，来源和运动参数仍归 Touch bar 设置。 |
| Touch bar Message / HUD / 决策层 | 部分 | 遮罩、焦点、警告和决策语义色 | 底层基础画布改变，语义遮罩不能被直接替换。 |
| 禁用或未分配 Key | 否 | 关闭状态 | 无内容时继续使用设备的关闭/黑屏语义，避免误示为可交互。 |

“受影响”只表示渲染器拥有且能够重新合成的背景像素。对全幅、不透明、已经预烘焙背景的素材，用户可能看不到背景色；这不是通过覆盖其像素来强制解决，而应通过保留透明源素材或重新生成派生图像解决。

## 9. 颜色与对比度规则

允许任意不透明颜色后，现有面向深色背景写死的浅色文字和深色卡片不能继续原样使用。统一调色板解析器至少应处理：

1. 根据背景相对亮度选择深色或浅色前景。
2. 从背景推导中性卡片面、弱文字和分隔线，避免直接复用固定深灰。
3. 保留业务语义色，但必要时调整其明度或为其增加对比边界。
4. 保证小尺寸 Key 上的主要文字、图标轮廓和交互状态可辨识。
5. 对极亮、极暗和高饱和颜色建立固定测试样例，避免只验证常规深色。

第一版不要求完整主题系统，但所有新增渲染代码应从 `RenderPalette` 获取中性色，不再新增散落的背景常量。

## 10. 渲染架构

配置流建议保持以下分层：

```text
DeckAppearanceSettings
        ↓
RenderPaletteResolver
        ↓
Layout / Key / Touch bar renderers
        ↓
RGB hardware frames
        ↓
HardwareSurface
```

约束如下：

- 不使用进程级可变全局颜色。
- 渲染入口显式接收外观设置或解析后的不可变调色板。
- `LayoutPlan` 可以携带外观版本或调色板引用，但不让硬件驱动理解产品设置。
- N4 Pro 适配器继续只负责尺寸、格式转换和下发，不自行读取设置或决定颜色。
- fake hardware 必须走与真实硬件相同的渲染结果，以便自动化测试覆盖。
- 当外观变更时，一次刷新应同时生成 Key 和 Touch bar 的一致快照，避免短暂出现两套背景。

## 11. 缓存与素材

当前多条路径缓存的是已经合成背景的 RGB 成品。外观设置如果不参与缓存身份，会出现用户保存新颜色后仍显示旧背景的问题。

### 11.1 通用规则

- 原始或归一化素材尽量保留 RGBA。
- 派生 RGB 图像的缓存键必须包含调色板标识或 `appearance_revision`。
- 外观变更后，失效所有依赖背景或中性色的派生缓存。
- 素材身份与渲染身份分离：改变背景色不应改变用户上传素材的 `asset_id`。

### 11.2 各类缓存

- App 图标和 URL 图标：保留可复用的透明源图，按调色板生成 Key 尺寸派生图。
- 自定义快捷键：继续以 `normalized.png` 作为源图，按当前外观重新生成 `key-*.png`；不能把旧 RGB 成品当作源图。
- 状态 Key：缓存键包含状态数据、尺寸和调色板标识。
- 宠物帧：预渲染签名包含素材指纹、尺寸和调色板标识；外观变化后重建帧。
- Touch bar 面板：任何整帧或局部面板缓存都包含 `appearance_revision`。
- Agent 动画：如果源帧已包含不透明背景，第一版实现前需要先补充透明源或建立可重复生成的派生流程。

## 12. 持久化与 API

外观配置应作为独立配置域持久化，例如：

```text
~/Library/Application Support/AgentDeck/deck-appearance.json
```

建议采用带版本的原子写入格式：

```json
{
  "version": 1,
  "background_color": "#F2E8D5"
}
```

恢复默认时：

```json
{
  "version": 1,
  "background_color": null
}
```

API 建议：

- `GET /ui/display-appearance`：读取当前生效值和 revision。
- `PUT /ui/display-appearance`：校验、持久化并应用独立外观设置。
- 聚合保存接口 `PUT /ui/configuration` 可以包含 `display_appearance`，但服务端仍按独立配置域验证和持久化。

若未来支持 TOML 启动配置，TOML 只作为没有用户持久化值时的初始默认，不覆盖用户已经保存的选择。

## 13. 应用与刷新流程

```text
编辑草稿
  → Web 预览
  → 保存并应用
  → 校验和原子持久化
  → 生成新 appearance_revision
  → 失效相关派生缓存
  → 用同一调色板重建当前 Key 与 Touch bar
  → 更新 LayoutPlan / frame revision
  → 常驻 renderer 按 latest-wins 下发
```

如果持久化或调色板解析失败，应保留旧设置和旧画面，不允许出现部分应用。硬件暂时断开时，设置仍可成功保存；设备重连后使用最新外观生成首帧。

## 14. 兼容性

- 现有用户没有外观配置文件时等价于 `background_color=None`。
- `None` 必须保持当前各渲染器的既有默认背景，而不是改成一个新的统一默认色。
- 旧自定义图标的 `normalized.png` 可继续作为重新生成来源；若只有不透明成品，则应保持原样并给出可诊断状态，不能破坏性猜测透明区域。
- 不改变现有 Key、Touch bar、PETS 或硬件设置文件的含义。
- 不改变设备握手、重连、亮度和输入事件合同。

## 15. 验收标准

### 15.1 自动化验证

- 未设置背景色时，代表性 App、URL、快捷键、状态 Key、宠物 Key 和 Touch bar 快照与改动前一致。
- 设置深色、浅色和高饱和背景后，覆盖矩阵中的基础背景像素都变为目标颜色。
- App、favicon、宠物和用户图片的非透明像素不因背景设置发生变化。
- 浅色背景下主要文字和图标使用可读的深色前景；深色背景下使用可读的浅色前景。
- 恢复默认后不再复用自定义背景派生缓存。
- 连续快速保存多个颜色时，最终硬件只呈现最新 revision。
- 配置文件能正确 round-trip，非法颜色不会改变现有设置。
- fake hardware 能观察到同一 revision 下同时更新的 Key 和 Touch bar。

### 15.2 Web 验证

- “显示外观”与“Touch bar 设置”是平级入口。
- PETS 配置中不出现背景色。
- 草稿改变只影响预览，点击“保存并应用”后才影响设备。
- “恢复默认”明确展示为未设置，而不是某个固定十六进制值。

### 15.3 N4 Pro 真机验证

- 选择一个与现有默认值明显不同的颜色，确认普通 App Key、自定义 Key、状态 Key、宠物 Key 和 PETS Touch bar 面板的可合成背景同时变化。
- 确认全幅不透明图片不会被错误染色。
- 切换浅色和深色后，检查文字、卡片和状态标识可辨识。
- 恢复默认后，确认现有视觉结果恢复。
- 切换外观不应触发额外握手、设备重新初始化或 HID 重连。

## 16. 预计实现触点

实现阶段至少需要检查并按职责修改：

- 外观配置模型、版本化存储和 Web API。
- Web 控制台独立设置入口、草稿模型和双表面预览。
- App、URL、快捷键、状态、宠物和 Touch bar 渲染入口。
- App/URL/custom shortcut/pet/status/Touch bar 的派生缓存键和失效逻辑。
- Layout revision 与常驻 renderer 的一致性刷新。
- fake hardware 快照和 N4 Pro 手工 smoke 文档。

具体文件名以实施时的当前代码结构为准，不在本设计中把配置读取写死到某个硬件驱动。

## 18. 与现有设计的关系

本设计补充但不替代以下既有设计：

- Key surface 配置仍定义 App、URL、自定义快捷键等内容如何绑定到物理按键。
- 状态 Key 设计仍定义状态信息和业务语义色。
